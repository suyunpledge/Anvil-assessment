# 部署、发布与效果复现

## 适用范围与资源

本次可复用主线是 **Windows x64 + Python 3.12 + 本地 Ollama 的代码 Agent**。支持本地浏览器工作台；默认监听 `127.0.0.1:8099`，模型服务默认 `127.0.0.1:11434`。跨系统部署和多用户公网服务不是本次验收范围。

| 环境档位 | 锁文件 | 用途与外部资源 |
|---|---|---|
| `code` | `deploy/requirements-windows-py312-code.lock` | 最小代码服务；`qwen2.5-coder:7b`；启动时 `ANVIL_HR=0` |
| `test` | `deploy/requirements-windows-py312-test.lock` | 全部离线回归，加 HR/Pillow 等测试依赖；无需模型、检测权重、PyTorch。真实代码验收另需代码模型 |
| `full` | `deploy/requirements-windows-py312-full.lock` | 全部集成依赖；记忆另需 `bge-m3:latest`，视觉另需 `qwen2.5vl:7b` 和合法取得的 YOLO 权重 |

代码模型 tag 与适配器必须匹配 `anvil.toml`。模型权重、视觉素材、用户项目和 `.runtime/` 不随源码分发。内存/显存能否满足取决于量化、上下文和同时加载的模型；CPU 回落可能显著增加耗时。先做 doctor，再做真实验收，不能用最低配置承诺替代实测。

依赖锁固定直接与传递依赖版本，限定 Windows/Python 3.12；不包含 wheel 哈希，不保证软件源永久保留这些版本。需长期/离线复用时应同时保存 wheelhouse、摘要、模型文件和其使用授权。

## A. 从平台源码或交付包安装

从发布的固定提交取得源码，或下载 `Anvil-assessment.zip` 及旁边的 `.sha256`，解压到新的目录。不要复用其他环境的 `.venv`；已有本地修改的目录不要直接覆盖。

```powershell
# 与发布页公布的 SHA-256 比对
Get-FileHash .\Anvil-assessment.zip -Algorithm SHA256
Expand-Archive -LiteralPath .\Anvil-assessment.zip -DestinationPath .\Anvil-release
Set-Location .\Anvil-release

# 标准库即可核对 ZIP 内成员、文件 SHA-256；多出/缺失/篡改均失败
py -3.12 scripts/pack.py --verify ..\Anvil-assessment.zip

# 创建 .venv，按锁文件安装，并执行 pip check；失败时停止
.\deploy\bootstrap.ps1 -Profile code

# 安装并启动 Ollama 后准备配置中规定的代码模型
ollama pull qwen2.5-coder:7b
.\start.ps1 -CodeOnly -Doctor
.\start.ps1 -CodeOnly
```

打开 `http://127.0.0.1:8099/console`，将本目录 `.runtime/service-token` 的内容填入右上角。每个独立部署生成自己的令牌；数据接口要求令牌，`/health` 仅用于进程探活。资源检查使用 `/integrations?scope=code`；工作台的完整模块状态仍可能提示未安装的可选模块，这不等同于代码主线失败。停止用 Ctrl+C。

若 PowerShell 策略阻止执行脚本，按组织允许的方式运行脚本，或手工执行等效的 `py -3.12 -m venv .venv`、`.venv\Scripts\python.exe -m pip install -r <锁文件>` 和 `python anvil.py`。不要求修改系统级执行策略。

`-CodeOnly` 在启动终端设置 `ANVIL_HR=0`。切回记忆/完整模式时先 `Remove-Item Env:ANVIL_HR -ErrorAction SilentlyContinue`。自定义配置使用 `ANVIL_CONFIG` 的绝对路径，模型地址可用 `LOCAL_LLM_OLLAMA` 覆盖；应把最终生效配置作为部署记录保存。

## B. 验收与预期结果

最小部署可先直接运行真实代码验收：

```powershell
.\.venv\Scripts\python.exe scripts/integration_e2e.py --scope code
```

脚本创建独立端口、令牌、项目和运行目录，只确认它自己创建的演示工单，结束时停止它启动的服务。通过标准是 `report.json` 的 `ok=true`、三道 gate 通过、确认前不落盘、确认后修改有效、原测试及无关函数保持不变、5 个独立边界用例通过。出错会以非零退出码和失败报告结束；原始报告保留在输出所示目录。

准备完整考核附件时安装 `test` 档位、Node.js 22，再执行：

```powershell
.\deploy\bootstrap.ps1 -Profile test
.\.venv\Scripts\python.exe scripts/assess.py --live --scope code
```

流水线未安装模型时，`python scripts/assess.py` 只执行离线检查与源码包校验；真实推理结果以部署机上的 `--live` 验收为准。assess.py 要求输出目录不存在，且报告生成期间源码保持不变。

### 可选的记忆与视觉

```powershell
.\deploy\bootstrap.ps1 -Profile full
ollama pull bge-m3:latest
ollama pull qwen2.5vl:7b
# 将合法取得的 yolov8n.pt 放入 .runtime/models/，或修改 vision.weights
.\.venv\Scripts\python.exe anvil.py --doctor --scope full
.\.venv\Scripts\python.exe scripts/assess.py --live --scope full --vision-image C:\素材\bus.jpg
```

仅验收记忆可用 `--scope memory`，不要求视觉模型和权重。完整模型安装可能占用较多带宽及磁盘，不包含在“几分钟运行演示”的耗时中。不要将单张公交车样本代码当作通用图片分类器。权重和第三方组件分发说明见 `vendor/NOTICE.md`。

## C. 锁定与复现效果

接收方应记录并比较：源码 ZIP 哈希/内部文件清单、固定提交、Python/包版本、`anvil.toml`、模型 digest、测试输入、模型调用预算、硬件、验收结果。Ollama 的模型列表包含 digest，用于识别实际本地模型；仅记录可变 tag 不足以证明模型相同。[Ollama 模型列表接口](https://docs.ollama.com/api/tags)

本项目的复现目标是**相同任务满足相同验收行为**，不保证 LLM 每次生成相同代码字节。ZIP 在相同源码、来源元数据与压缩运行时下重复构建应逐字节一致；`assess.py` 自动比较两次产物。SHA-256 解决内容完整性检查，不能替代发布者身份认证。

如模型 digest 不同，应先保存差异并重新验收；不要在报告中写成同一模型。为长期复现，可按组织许可归档模型及 Ollama 版本，保存与 `ollama show` 对应的模型信息。更换嵌入模型或维度后必须重建索引，避免混用旧向量。

离线准备示例（联网机器也需相同 Windows/Python 架构）：

```powershell
py -3.12 -m pip download --only-binary=:all: -r deploy/requirements-windows-py312-test.lock -d wheelhouse
Get-ChildItem .\wheelhouse -File | Get-FileHash -Algorithm SHA256 | Export-Csv .\wheelhouse-sha256.csv -NoTypeInformation
# 接收方先比对 wheelhouse 摘要，再安装
.\deploy\bootstrap.ps1 -Profile test -Wheelhouse C:\离线资产\wheelhouse
```

更新依赖时，先在独立环境升级和验收，再使用 `scripts/lock_dependencies.py` 从该环境导出依赖闭包；不要直接对整个开发环境 `pip freeze`，其中可能包含其他项目和本地 editable 路径。

## D. 发布到 GitHub / Azure DevOps

仓库已提供两套配置，选择平台后提交源码、文档、依赖锁和流水线配置。`.runtime/`、模型权重、令牌与个人项目记录不进入版本库。

**现有 GitHub 仓库路线：** `.github/workflows/assessment.yml` 在 `main` 推送、PR 或手动触发时，在 Windows runner 安装测试锁文件，执行离线验收并上传 `publish/`。在 Actions 结果页下载附件，复制运行 URL、提交 SHA、产物 SHA 到考核总览。附件配置保留 30 天；长期资产需另在版本发布页保留 ZIP、摘要和部署文档。GitHub 支持通过 `upload-artifact` 保存测试及构建产物。[GitHub 官方产物文档](https://docs.github.com/en/actions/tutorials/store-and-share-data)

**Azure DevOps Services 路线：** 将分支放入指定 Azure Repos，或连接现有 GitHub 仓库；在 Pipelines 选择仓库根 `azure-pipelines.yml`。成功运行后在产物中下载 `Anvil-assessment`，登记仓库、运行 URL 和提交 SHA。该 YAML 使用 `PublishPipelineArtifact@1`；若组织采用 Azure DevOps Server，应按其支持的产物任务调整，不能假定 Services 配置直接兼容。[Azure Pipelines 官方产物文档](https://learn.microsoft.com/en-us/azure/devops/pipelines/artifacts/pipeline-artifacts?view=azure-devops)

两套 CI 都不下载模型、不调用付费 API，失败时保留报告便于排查。流水线产物为离线检查结果与源码包；模型效果由部署机器上的 `--live` 验收与新环境复现记录补足。

## E. 运行数据、升级与回退

运行数据默认在 `.runtime/`；可用 `LOCAL_IDE_RUNTIME` 指定独立目录。不要让两个实例共用同一运行目录。日志可能含源码，应只分享本次合成演示的记录。模型生成代码会以本地账户执行：现有资源/环境限制不构成完整网络和文件系统隔离，按组织要求在专用账户或虚拟机演示。

升级前停止服务，保存旧源码/锁文件和需要保留的运行数据；在新目录安装新版本，用新运行目录完成验收，再切换。回退时停止新版，恢复旧版本及与其匹配的数据备份。项目记忆按绝对项目路径识别；移动项目后默认视为新项目，不能期待旧路径记忆自动迁移。令牌不随交付包迁移，工作台需重新填写新实例令牌。

## F. 常见故障

| 现象 | 排查与处理 |
|---|---|
| doctor 的 `ollama:unavailable` | 检查 Ollama 正在运行、配置地址和网络闸；不要把 `/health` 成功当模型就绪 |
| `model:code` | 检查 tag 与 `anvil.toml` 完全一致；准备对应模型后重试 |
| 只缺嵌入/视觉，代码考核无法演示 | 用 `--scope code` / `-CodeOnly`，报告明确该范围 |
| pip 无法找到固定版本 | 使用组织镜像/已校验 wheelhouse；若改版本，重新生成锁和验收，不忽略错误继续 |
| 401 | 使用当前实例的令牌；检查是否读到了旧运行目录 |
| 429 | 当前工单/推理队列达到上限；等待或取消已知工单，再按硬件调预算 |
| `needs_input` / `escalated` / 超时 | 查看当次工单及模型记录；检查模型能力、预算、上下文和硬件，保留失败结果 |
| hash 不符 / 解包验证失败 | 重新取得同一版本的包与预期摘要 |
| HR 入库延迟 | 检查嵌入模型、维度、待入库队列和日志；恢复后重试 |
